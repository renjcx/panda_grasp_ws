# 物理参数与夹爪力控

> 项目最后一道没关死的门：为什么 20g 的方块有时夹不住、有时直接消失？这要从 Gazebo 的物理参数和"位置控制"的原理讲起。

---

## 一、物理引擎：Gazebo 的"牛顿定律计算器"

Gazebo 不只是画面，它每时每刻都在算物理：重力让物体下落、碰撞让物体互相阻挡、接触面产生摩擦。干这活的程序叫**物理引擎**。本项目在 `worlds/grasp_world.sdf` 里的选择：

| 参数 | 值 | 大白话 |
|------|-----|--------|
| `physics type` | bullet-featherstone | Bullet 引擎的 featherstone 算法分支 |
| `max_step_size` | 0.001（1ms） | 每 1 毫秒把整个世界的物理重新算一遍 |
| `real_time_factor` | 1.0 | 仿真时间 = 真实时间（实时跑） |

选型历史：当初选 bullet-featherstone 是冲着"支持 mimic 关节"去的（SDF 里的旧注释也这么写），后来实测证明**当前软件栈下没有任何引擎能提供可用的 mimic 约束**（详见 [`夹爪单指运动问题修复记录.md`](夹爪单指运动问题修复记录.md)）。所以现在引擎选型和 mimic 无关，保留即可。

> ⚠️ 1ms 步长是精度与速度的折中：步长越小算得越准、算得越慢。轻物体在接触瞬间的速度可能被算出异常大——这是"方块偶尔消失"的一个可疑来源（见第四节）。

---

## 二、世界里的三个物体（grasp_world.sdf 怎么写的）

| 物体 | static | 关键参数 | 为什么这样写 |
|------|--------|---------|-------------|
| 地面 | ✅ 静态 | 10×10 平面 | 永远不动的东西声明成 static，物理引擎直接跳过它的动力学计算，省算力 |
| 桌子 | ✅ 静态 | 2×2×0.1，中心 x=0.5，顶面 z=0.10 | 中心 z=0.05 + 半厚 0.05 = 顶面 0.10 |
| 绿色方块 | ❌ 动态 | 0.03³，20g，摩擦 μ=1.0，中心 (0.6, 0, 0.115) | 要被抓的物体必须动态，物理引擎才"管"它 |

几个数字的来源（面试常被追问"这些数怎么来的"）：

1. **方块坐标 z=0.115**：桌面中心 0.05 + 桌面半厚 0.05 + 方块半高 0.015 = 0.115，正好"坐"在桌面上（SDF 里留了这条公式注释）。对应地，机器人 spawn 时 `-z 0.1` 抬升，让底座正好落在桌面顶面。
2. **惯量 3e-6**：正方体惯量公式 I = m·(a²+b²)/12 = 0.02 × (0.03² + 0.03²)/12 = 3×10⁻⁶，SDF 里的 `0.000003` 就是这么算出来的。
3. **摩擦 μ=1.0**：ODE 摩擦模型里的摩擦系数，1.0 已经是高值（约等于橡胶对橡胶）——所以"滑落"不是摩擦没给够，问题在别处（见第四节）。

## 三、控制器的"肌肉"参数（panda_controllers.yaml）

控制器怎么把"目标角度"变成"关节真的转过去"？看这组参数：

| 参数 | 值 | 大白话 |
|------|-----|--------|
| `update_rate` | 100Hz | 控制器每 10ms 检查一次"到没到目标"，差多少补多少 |
| command 接口 | 只有 position | 控制器只能命令"转到哪个角度" |
| state 接口 | position / velocity / effort | 能读回"现在多少度 / 多快 / 受多大力"——**effort 只读不写** |

夹爪关节配了 PID 增益（手臂没配，用 gz_ros2_control 位置接口内部的默认参数）：

| 参数 | 值 | 大白话 |
|------|-----|--------|
| P（比例） | 500 | 差 1 个单位就输出 500 个单位的纠正——差得越多，纠得越猛 |
| I（积分） | 10 | 把长期攒下的小误差拿来纠正，消除"差一点到不了"的稳态误差 |
| i_clamp | 50 | 给 I 设上限，防止它攒太大导致冲过头（积分饱和） |
| D（微分） | 5 | 按误差变化速度"刹车"，防止到位时刹不住、来回震荡 |
| ff_velocity | 0 | 速度前馈，本项目不用 |

## 四、位置控制 vs 力控：为什么 20g 方块是个难题

### 位置控制的原理和盲区

本项目夹爪是**位置控制**：命令只有"手指转到 0.04m（开）或 0.0m（关）"。控制器只保证"**到了这个角度**"，完全不关心"**用了多大的力**"。

闭合 3cm 方块时实际发生的事：

```
命令"手指转到 0.0"
  → PID 看到误差，发力推动手指
  → 手指碰到方块，方块被推着走（摩擦不足就滑脱）
  → 手指继续压，直到物理上压不动（缝隙归零）
  → 手指"到了"，任务完成——但夹持力多大？没人设定过，也没人知道
```

**夹持力 = 方块的反作用力，是个被动的结果，不是被控制的量。** 对 20g 的轻物体：

- 它惯性极小，手指一碰就容易**被推走、弹飞**，而不是被稳稳夹住；
- 摩擦不足以自锁就会**滑落**——这个问题已由双指同步修复解决（实测抓取成功，见修复记录）；
- 最坏情况：接触瞬间被算出异常大的冲量，方块**穿过桌面或飞出视野**——这就是"方块偶尔消失"最可能的机理：**轻物体在接触求解中的数值不稳定**，与摩擦参数关系不大，跟质量、仿真步长、接触模型有关。

### 力控是什么，为什么本项目没有

力控把目标从"角度"换成"力"：比如"夹到 5N 就停"。好处是夹轻物时力自然变小，不会把物体挤飞；真机 Franka 就是用关节力矩做阻抗控制的。

但力控需要两块砖，本项目一块都没有：

| 需要的 | 本项目现状 |
|--------|-----------|
| **effort command 接口**（命令"关节用多大力"） | ❌ 硬件接口只声明了 position command（`panda.urdf.xacro`），effort 只有 state（可读不可写） |
| 力/力矩反馈 | ⚠️ effort state 接口能读回关节力矩（间接看到夹持力），但还没有利用起来 |

### 三条出路

| 路线 | 做法 | 评价 |
|------|------|------|
| 力控（正路） | 加 effort command 接口 + 读 effort 反馈，做阻抗控制 | README 未来规划里的"力控抓取"，改动大 |
| 调物理参数（快路） | 软接触模型（接触刚度/阻尼）、加大摩擦、加大方块质量、放慢闭合速度 | 能缓解"消失/滑落"，但治标 |
| 开环柔顺（仿真常用 trick） | 闭合速度放慢 + 手指目标位略小于物块宽度，靠摩擦自锁 | 不引入力控也能夹住，下一步最容易做的实验 |

---

## 五、一句话总结

物理引擎算世界，位置控制只有"角度"一个目标、没有"力"的概念——**夹 20g 轻物时，夹持力是个没人管的被动结果**，轻物就在"被推走 / 弹飞 / 消失"之间碰运气。要么调物理参数（快），要么上力控（正）。
