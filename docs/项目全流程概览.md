# 项目全流程概览

> 从零到实现抓取的完整阶段划分。先讲主干，细节可结合其他文档深入。

---

## 项目一句话概括

在电脑上搭一个**虚拟的 Franka Panda 机械臂**，让它自动完成：**移动到绿色方块上方 → 下降 → 闭合夹爪 → 抬起**。全程是仿真（Gazebo），不碰真实硬件。

## 一张图看懂全流程

```
① 装环境
   ROS 2 Jazzy · Gazebo Harmonic · MoveIt 2 · ros2_control
   │
   ▼
② 建模型（图纸）
   franka_description（官方） ──include──▶ panda_grasp_sim/urdf/panda.urdf.xacro
   │
   ▼
③ 进 Gazebo（物理世界 + 肌肉）── launch/sim.launch.py 编排
   panda.urdf.xacro ──xacro 展开──▶ /robot_description ──spawn──▶ Gazebo 实体
   config/panda_controllers.yaml ──▶ 3 个控制器（胳膊 / 夹爪 / 状态广播）
   │
   ▼
④ 装大脑 ── panda_moveit_config（Setup Assistant 用干净 URDF 生成）
   panda.urdf.xacro ──剥掉仿真段──▶ config/panda.urdf（URDF 快照）
   快照 ──向导生成──▶ panda.srdf + kinematics / ompl_planning
                     + joint_limits / moveit_controllers 等 yaml
   MoveItConfigsBuilder 把全部文件打包成一份配置（④⑤ 共用）
   sim_with_moveit.launch.py = ③ 整条链 + move_group + RViz
   │
   ▼
⑤ 写脚本 ── pick_place_full.py（MoveItPy）
   读 /joint_states → IK + OMPL/Pilz 规划 ──action──▶ 发回 ③ 的控制器
   │
   ▼
⑥ 调试修复（贯穿全程）
   3 个 MoveItPy bug · Gazebo 资源路径坑 · 夹爪单指问题
```

运行时数据流（③④⑤ 拼起来后，一条命令的完整闭环）：

```
   你的命令（RViz 拖拽 / pick_place_full.py）
     │
     ▼
   move_group ── 读 /joint_states 维护当前状态 → IK → OMPL 规划出轨迹
     │ /fp3_arm_controller/follow_joint_trajectory（action）
     ▼
   controller_manager（Gazebo 内部）── 100Hz 插值 → 关节转动
     │
     └──▶ joint_state_broadcaster → /joint_states
            └──▶ robot_state_publisher → /tf（move_group / RViz 靠它知道各连杆位置）
```

## 六大阶段

### ① 装环境

安装 ROS 2 Jazzy（机器人软件框架，负责各程序之间通信）、Gazebo Harmonic（物理仿真引擎）、MoveIt 2（运动规划库）、ros2_control（关节控制框架）。

**作用**：这是地基，后面所有东西都跑在这上面。

### ② 建机器人模型（franka_description 包）
用 URDF/Xacro 格式写机械臂的"图纸"：7 个手臂关节 + 夹爪的尺寸、连接关系、质量、关节限位。这个包是 Franka 官方开源的，直接拿来用。

官方包自带 `robots/fp3/fp3.urdf.xacro`（纯模型图纸，能显示外形但动不了）。导入后做的事：
1. **复用官方宏** — 在项目自己的 `panda.urdf.xacro` 里 include 官方宏文件，加载 fp3 的 4 个参数文件（关节限位 / 运动学 / 惯量 / 动力学）
2. **调用宏生成整条臂** — 传 `robot_type=fp3`、`hand=franka_hand`、`ros2_control=false`（关掉官方的真实硬件接口，仿真不用）
3. **补仿真专属内容**：
   - `world` 固定关节 —— 把机器人锚定到世界坐标系
   - ros2_control 块 —— `GazeboSimSystem` 插件 + 8 个关节的 command/state 接口 + 初始角度
   - gazebo 插件标签 —— 指向控制器配置 `panda_controllers.yaml`
4. **launch 时展开** — `xacro.process_file()` 展开成纯 URDF → 发布为 `/robot_description` → robot_state_publisher 据此发 TF，Gazebo 据此生成实体

> **为什么夹爪只有一个自由度？** 真实 Franka Hand 只有一个电机、两指机械耦合，物理上就是 1 个自由度，规划时不应有两个独立自由度。
> **但为什么 URDF 里两个手指是独立关节？** 因为 Gazebo Harmonic 的物理引擎**不执行 URDF mimic 约束**（已知上游 bug，`gazebosim/gz-sim#1684`，服务器日志会报 "does not support mimic constraints"），只声明 mimic 会导致 `finger_joint2` 完全不受控——只有一个手指会动。
> **实际架构**：物理层两个手指都是普通关节，由 `fp3_gripper_controller` 用相同的位置命令**同步驱动**；规划层在 `panda.srdf` 里声明 `<mimic_joint>`，让 MoveIt 仍把它当作 1 个自由度，且生成的轨迹自动展开两个手指关节。
> 完整排查过程见 [`夹爪单指运动问题修复记录.md`](夹爪单指运动问题修复记录.md)。

### ③ 让机器人在 Gazebo 里"活"起来（panda_grasp_sim 包）
两件事：**把图纸装进物理世界**（有重力、有碰撞、有摩擦），**给机器人接上肌肉**（能接收命令、驱动关节）。
| 文件 | 管什么 | 一句话 |
|------|--------|--------|
| `worlds/grasp_world.sdf` | 仿真世界 | 搭场景：地面 + 桌子 + 绿色方块 |
| `urdf/panda.urdf.xacro` | 图纸 + 硬件接口 | 给图纸补上"接物理引擎的插头" |
| `config/panda_controllers.yaml` | 控制器配置 | 定义 3 个控制器：报状态、动胳膊、开夹爪 |
| `launch/sim.launch.py` | 启动编排 | 按正确顺序拉起所有进程 |

      ####  launch 编排 `sim.launch.py` —— 顺序启动，缺一不可
```
T+0s   设 GZ_SIM_RESOURCE_PATH（否则 Gazebo 找不到 mesh → 白屏）
       ├─ 启动 Gazebo（加载 grasp_world.sdf）
       ├─ 启动 robot_state_publisher（xacro → URDF → 发 /tf）
       └─ 启动时钟桥（Gazebo 时钟 ↔ ROS 时钟，不桥接 /tf 时间戳会错乱）
T+3s   等 Gazebo 就绪 → 把 /robot_description 发给 Gazebo 生成实体
T+6s   等机器人出生 → 加载 3 个控制器
```

为什么要排队：**controller_manager 不是独立进程**，它是 gz_ros2_control 插件在 Gazebo 内部启动的——机器人还没生成，它就不存在，spawner 会直接超时。

**作用**：一条命令 `ros2 launch panda_grasp_sim sim.launch.py` 拉起整条链。验证方式：`ros2 run panda_grasp_sim hand_grasp_test`（夹爪张开 → 闭合 → 再张开）。

####  至此的控制链路
```
你的命令
  → /fp3_arm_controller/follow_joint_trajectory（action）
  → 控制器插值（100Hz）
  → controller_manager → gz_ros2_control 插件
  → Gazebo 物理引擎（算重力/碰撞/摩擦）
  → 关节转动 → 3D 画面更新
```
**作用**：到这一步，机械臂在物理世界里"活"了——能报状态、能动、能夹。阶段④的 MoveIt 和阶段⑤的抓取脚本，最后都是走这条链路来驱动它的。

> 深入阅读：[`Launch文件详解.md`](Launch文件详解.md)（逐段讲 launch 文件）、[`Gazebo踩坑总结.md`](Gazebo踩坑总结.md)（本阶段踩过的 6 个坑）


### ③.5 插曲：TF —— 机器人的"定位系统"

**一句话**：TF 是一张实时更新的换算表，回答"机器人的某个部件现在在世界地图的哪个位置"。抓取任务从头到尾（写目标、查现状、画出来）都在用它。

#### 坐标系是一棵"族谱树"

URDF 图纸里每个连杆（link）自带一个坐标系，靠关节串成父子关系。规则只有一条：**每个连杆只记录"我相对我爸偏移了多少"**——想知道某个连杆相对老祖宗 `world` 在哪，就沿着族谱一路换算上去：

```
world（老祖宗：仿真世界的原点，一切位置的参照）
  └─ world_fixed 固定关节：把机器人钉在世界原点上
       └─ base（机器人底座）
            └─ fp3_joint1~7 旋转关节：每个转多少，后面的子孙跟着转多少
                 └─ fp3_hand（手掌）
                      └─ fp3_hand_tcp（指尖，所有换算的终点）
```

#### 谁在算：robot_state_publisher

机器人在动，族谱每时每刻在变，需要有个"会计"专门算。robot_state_publisher 干的就是：

```
关节角（/joint_states，由阶段③ 的 joint_state_broadcaster 从 Gazebo 里读出来）
   + 图纸（URDF，父子之间固定的偏移）
   = 顺着族谱从根算到指尖 → 每个连杆在世界里的位置姿态
   → 发到 /tf 话题（谁想知道，谁去订阅）
```

#### 抓取任务里 TF 的三次出场

1. **写目标**：脚本里"去方块上方 (0.58, 0, 0.215)"是用 world 坐标说的位置。机械臂只能转关节，把"world 里的目标点"翻译成"7 个关节各转多少"就是 IK。**正着算是 TF（关节角 → 位置，robot_state_publisher 干），反着算是 IK（位置 → 关节角，MoveIt 的 KDL 干），两者用的是同一份图纸**。
2. **查现状**：动手前要知道"指尖现在在哪、朝哪个方向"。脚本问一句 `lookup_transform("world", "fp3_hand_tcp")`，意思是"帮我查：指尖在 world 里的当前位置姿态"——查到的朝向直接拿来当规划的起点朝向。
3. **画出来**：RViz 的 Fixed Frame 设为 world，机器人、方块、桌子谁在谁的哪边，全部按 /tf 这张表来画。表不准，画面就散了。

> ⚠️ 一个相关的坑：TF 每条记录都带时间戳，Gazebo 的时钟必须桥接给 ROS（阶段③ 的时钟桥），否则"查表"会失败。这就是全项目节点都开 `use_sim_time` 的原因。


### ④ 接入 MoveIt 2（panda_moveit_config 包）

**作用**：给机器人装"大脑"。你只说"末端去桌子上的某点、掌心朝下"，MoveIt 通过**逆运动学（IK）**自动算出 7 个关节各转多少度，并用 OMPL 算法规划出一条**避障的关节轨迹**。RViz 面板让你能手动拖拽目标点、点 Plan 看规划结果。

#### 这个包回答的 4 个问题

MoveIt 是一套通用框架，本身不"认识"任何机器人——关于机器人的一切信息都来自配置包。`panda_moveit_config` 就是这份配置：

| MoveIt 要问的问题 | 答案 | 写在哪个文件 |
|-------------------|------|-------------|
| 关节怎么分组？ | `arm`（fp3_joint1~7）、`gripper`（手指关节） | `config/panda.srdf` |
| IK 用什么求解器？ | KDL 数值迭代求解器（7 轴臂常用） | `config/kinematics.yaml` |
| 用什么算法规划？ | OMPL 采样规划（绕障）；直线运动用 Pilz LIN | `config/ompl_planning.yaml` |
| 轨迹发给哪个控制器？ | 阶段③ 的 `fp3_arm_controller` / `fp3_gripper_controller` | `config/moveit_controllers.yaml` |

除上表外，SRDF 里还藏着三个细节：`<virtual_joint>`（world 坐标系挂接）、`<end_effector>`（声明夹爪手掌 `fp3_hand`）、`<disable_collisions>` 碰撞矩阵（37 对永远碰不到的连杆对，跳过自碰检查省算力）。其余重要文件：

| 文件 | 管什么 |
|------|--------|
| `config/panda.urdf` | **URDF 快照**：从 sim 包的 xacro 展开、剥掉 `<gazebo>`/`<ros2_control>` 段的干净图纸，只留几何结构 |
| `config/joint_limits.yaml` | 默认速度/加速度缩放 0.1（安全模式，与阶段⑤ 一致） |
| `config/panda.urdf.xacro` + `panda.ros2_control.xacro` | **mock 假硬件**（`mock_components/GenericSystem`）：不连 Gazebo 也能单独跑 MoveIt |
| `launch/*.launch.py` | Setup Assistant 生成的 8 个启动模板 |

#### 两处关键设计（都是踩坑换来的）

1. **双指 mimic 在 SRDF 层声明**：Gazebo 不执行 URDF mimic（见阶段②），物理层靠控制器同步驱动两指；MoveIt 侧在 `panda.srdf` 写 `<mimic_joint>`，规划时仍把它当 **1 个自由度**，生成的轨迹自动展开两个手指关节。
2. **URDF 快照不会自动同步**：`config/panda.urdf` 是生成那一刻的拷贝。改完 sim 包的 xacro 后，MoveIt 侧与 Gazebo 侧会加载**两份不同的结构**——改结构必须重新生成或手动替换快照。

> 这个包由 Setup Assistant 图形向导生成；完整生成步骤与"什么时候必须重新生成"见 [`panda_moveit_config生成指南.md`](panda_moveit_config生成指南.md)。

#### 启动编排 `sim_with_moveit.launch.py` —— 在阶段③ 之上叠加大脑

```
T+0s    Gazebo 全家桶（直接复用 sim.launch.py，阶段③ 整条链原样跑）
T+6s    等控制器就绪 → move_group 节点（运动规划引擎，MoveIt 的核心进程）
T+8s    等 move_group 就绪 → RViz（加载 config/moveit.rviz，带 MotionPlanning 面板）
```

两个节点共享**同一份配置**：`MoveItConfigsBuilder("panda", package_name="panda_moveit_config")` 把上面所有 yaml + URDF + SRDF 打包成一个参数字典，同时喂给 move_group 和 RViz（并开 `use_sim_time` 对齐 Gazebo 时钟）；阶段⑤ 的 MoveItPy 脚本也是用同一个 Builder 加载同一份配置。**配置只维护一份，图形界面、规划引擎、代码调用三个入口共用。**

#### 一次规划请求怎么走（MoveIt 内部流水线）

```
目标位姿（RViz 拖拽 / MoveItPy 脚本）
  → move_group
  → 请求适配器：校验起点越界、起点自碰（ompl_planning.yaml 前 4 项）
  → IK（KDL）：末端位姿 → 7 个关节角
  → OMPL 采样规划：关节空间随机采样 + 碰撞检测过滤 → 无碰撞路径
  → 响应适配器：时间参数化（给路径配上速度曲线，AddTimeOptimalParameterization）
  → 一条带时间戳的关节轨迹
  → /fp3_arm_controller/follow_joint_trajectory（action）
  → 进入阶段③ 的控制链路（100Hz 插值 → Gazebo → 关节转动）
```

MoveIt 只负责"想"（算轨迹），最后"动"仍走阶段③ 打通的那条控制链路——**两个阶段在这里咬合**。避障靠 PlanningScene 同时维护机器人模型和周围环境（桌面、方块）的碰撞体，采样出的每一段路径都要过碰撞检测。

#### 三条使用路径

| 路径 | 命令 | 说明 |
|------|------|------|
| 仿真 + 图形界面 | `ros2 launch panda_grasp_sim sim_with_moveit.launch.py` | RViz 拖拽目标球 → Plan → Execute |
| 纯规划调试（不开 Gazebo） | `ros2 launch panda_moveit_config demo.launch.py` | move_group + RViz + mock 假硬件，只验证规划不管物理 |
| 代码调用 | 阶段⑤ `pick_place_full.py`（MoveItPy） | 编程式规划，本项目最终形态 |

### ⑤ 写抓取脚本（pick_place_full.py）

用 MoveItPy 编程实现完整流程：

```
移动到预抓取点（方块上方）→ 张开夹爪 → 直线下降到抓取点 → 闭合夹爪 → 直线抬起
```

所有速度缩放到 0.1 倍（安全模式）。

**作用**：把阶段③④的能力串成一条自动流水线。

### ⑥ 调试与修复（贯穿全程）

过程中解决了 3 个 MoveItPy 兼容性 bug（参数名不匹配、规划管线加载失败、仿真时间下轨迹执行失败，详见 [`MoveItPy_Bug修复总结.md`](MoveItPy_Bug修复总结.md)）和 1 个 Gazebo 资源路径问题，踩坑过程已沉淀到 [`Gazebo踩坑总结.md`](Gazebo踩坑总结.md)。物理参数与"位置控制 vs 力控"的解读见 [`物理参数与夹爪力控.md`](物理参数与夹爪力控.md)。

## 一句话总结

整体就是 **"图纸 → 物理世界 → 肌肉 → 大脑 → 编排成流水线"** 这样一条线。
